Crypto Agent 架构说明
基于本地源码更新于 2026-06-20

一个长驻 daemon 驱动的加密交易 Agent

这个项目不是一个简单的命令行聊天机器人。当前实现是两进程架构： daemon 持有账户身份、策略、交易执行、SQLite 和 LangGraph agent runtime， CLI 只是通过 Unix socket 连接的薄客户端。

先纠正一个容易误读的点

README.md 还保留了早期 “CLI -> Agent Loop -> LLM” 的图。 当前代码的实际边界是 CLI -> IPC -> daemon -> LangGraph Agent / Strategy / Exchange。 本页按代码实现解释，不按旧 README 图解释。

心智模型

可以把 daemon 理解成交易控制平面。它持有账户身份、风险闸门、策略运行时、 心跳、cron 循环和持久化。客户端可以随时连接或断开，但不拥有交易状态。

两条执行路径

慢路径：LangGraph 节点循环调用模型和工具。快路径：市场数据触发策略信号，绕开 LLM 延迟。 两条路径最终都会落到共享的交易所抽象和风险控制原语上。

系统地图

关键边界不是“LLM vs tools”，而是“有状态 daemon vs 可替换客户端”。 所有可能影响资金的能力都放在 daemon 进程后面。

身份映射

这次重构最重要的修正不是换框架，而是把“钱、交易账户、bot、会话”从隐含全局状态拆成可审计的持久映射。 当前实现仍是保守的单 daemon 默认 bot，但交易、挂单、持仓和策略已经带上 bot/account 归属。

1. 资金账户

funding_accounts 表示资金池或资金所有者。默认实现创建 default-funding，基础币种默认 USDT。

运行流程

使用标签切换几条主流程：聊天请求、身份绑定、自主执行、重启恢复，以及风险/下单串行化。

客户端发送聊天

IpcClient.startChat() 写入 JSONL chat 消息，包含 session、requestId 和内容。

daemon 持久化用户回合

handleChat() 解析会话，保存用户消息，然后调用 agent.chatInSession()。

Agent 准备图输入

chatInSession() 做 micro/auto compact，注入 world snapshot，再把消息交给 LangGraph runtime。

LangGraph 循环到结束

call_model 产出 assistant 消息；如果存在 tool call，就进 tools 节点后回到模型。

src/ipc/client.ts:92src/daemon.ts:291src/agent.ts:137src/agent/langgraph-runtime.ts:46

恢复 daemon 选择

启动时先恢复 active_soul、active_exchange 和 active_user_session_id。

确保默认身份

ensureDefaultIdentity() 创建或刷新 funding account、trading account 和 bot。

会话绑定 bot

系统会话和用户会话通过 sessions.bot_id 归属到当前 active bot。

记录随交易流动

交易、挂单、持仓和策略写入时都携带 bot/account 字段，避免事后靠全局状态猜。

加锁并恢复状态

acquireDaemonLock() 防止重复启动；随后 daemon 恢复 soul、exchange、identity、sessions 和策略状态。

对账交易状态

启动时恢复 active positions，并把 pending orders 与交易所 open orders 对账。

心跳、cron、快路径

心跳和 cron 循环启动；快路径要么监听活跃策略，要么报告 idle。

一个全局互斥锁

慢路径 buy/sell 工具和快路径 executor 在 daemon 进程内共享 tradeLock。

持久化状态

持久化设计遵循一条实用规则：只有当丢失状态会造成资金损失、审计缺口、 风险控制绕过或严重用户体验退化时，才应该持久化。

账户身份状态
funding_accounts、trading_accounts、trading_bots 和 sessions.bot_id 共同描述“谁的钱、哪个交易账户、哪个 bot、哪段会话”。 daemon_state 额外保存 active identity 指针，便于重启恢复。
崩溃恢复状态
active_positions 保存本地 SL/TP 元数据。pending_orders 跟踪等待成交的订单。 daily_pnl 和 portfolio_watermark 避免风险限制在重启后被重置。
Agent 记忆状态
sessions, conversations, session_summaries, daemon_state, strategies 和 strategy_kb 保存用户上下文、active identity 和策略研究结果。

运维流程

常规流程是先构建，再运行 daemon，然后连接 CLI。生产使用时，用户级 systemd 服务运行构建后的 daemon。

本地命令 
npm run build
npm run daemon              # 前台运行 daemon
npm run dev                 # 连接 CLI 客户端
npm test                    # 运行 Vitest 测试
npm audit --audit-level=low # 依赖审计
用户级服务 
npm run install:service
systemctl --user start crypto-agent
systemctl --user status crypto-agent
tail -f ~/.local/state/crypto-agent/daemon.err
当前可观测性注意点
Heartbeat 通过 HeartbeatScheduler 运行，但 "All clear" 结果不会持久化。 持久化设计文档明确把 heartbeat 最近运行元数据延后实现。如果需要可审计的 uptime 和健康检查， 应增加 daemon_state.last_heartbeat_at、last_heartbeat_result，或记录所有 heartbeat 结果。
